# Worktrees

A git worktree is a second checkout of the same repository, on its own branch, in its own directory. An agent worker can run in one, so parallel workers never edit the same files. The design and its reasoning are in [design/worktrees-plan.md](design/worktrees-plan.md).

## Isolation

Spawn with isolation `worktree`: `tl spawn --worktree`, `tl new --worktree`, or `isolation: "worktree"` on the MCP `spawn` tool. A worker agent node (any harness) spawned without saying gets `worktrees.isolation` from the config (default `none`). The daemon creates `<main checkout>/.claude/worktrees/<nodeId>` on branch `tl/<nodeId>` (the prefix is `worktrees.branchPrefix`) from the tip of its base branch. It copies the gitignored files listed in `.worktreeinclude` (such as `.env` or `node_modules/`), or those matched by `worktrees.include` when set, and starts `claude --worktree <nodeId>` from the main checkout, which makes Claude keep the agent inside the worktree; Pi and Codex start directly in the worktree. The repo needs at least one commit, and Claude must already trust it (run `claude` in it once). Trust is checked in the node's [Claude account](harnesses.md#claude-accounts): run `claude` in the repo once under that account. A node spawned without isolation into a path inside a worktree shares that worktree, and its system prompt says so.

The base is the branch the worker forks from and is merged back into. Name it with `tl spawn --worktree --base NAME`, `tl new --worktree --base NAME`, or `base` on the MCP `spawn` tool; when that branch does not exist, tiller creates it as a plain branch (no checkout) at the HEAD of the checkout the spawn's `cwd` is in. Every worker of one task should get the same base, so their merges accumulate on it and a later worker starts from the earlier ones' merged work. Without `base`, the base is the branch checked out at `cwd`, so a worker that spawns from its own worktree branches from its own work. If that branch is protected (see Merging) or HEAD is detached, tiller instead creates a task branch named by `worktrees.taskBranch` (default `tl/{slug}`, where the slug is the node's title in lower case with dashes, at most 40 characters), adding `-2`, `-3` and so on when the name is taken. The spawn reply, `list_nodes` and `tl list` show the base.

## Read-only worktrees

A reviewer, auditor or researcher that needs its own checkout but never commits can spawn with isolation `detached`: `tl spawn --detached`, `tl new --detached`, or `isolation: "detached"` on the MCP `spawn` tool (a preset or `worktrees.isolation` may set it too). The daemon creates the same `<main checkout>/.claude/worktrees/<nodeId>` directory with HEAD detached at the tip of `base`, and no branch. `base` must be an existing branch; without it the worktree checks out the HEAD of the checkout `cwd` is in, and no task branch is made. The include copy and `worktrees.setup` run as for any worktree, so a reviewer can run the tests. Rows, `list_nodes` and `tl list` show `⎇ detached @ <base>`.

Merging a read-only node is refused: it has no branch. Closing it skips the branch checks and removes the worktree, but the dirty check still applies, and commits made on the detached HEAD that are not in the base count as unmerged: the close is refused and says the worktree is read-only (detached). `--keep-branch` (`worktree: "keep"`) then commits any changes as WIP and puts the commits on a new `<branchPrefix><nodeId>` branch before removing the directory; `--discard` drops them. One value of `isolation` was chosen over a `readOnly` flag beside `worktree` so the spawn schema, presets, the config default and the CLI cannot express a read-only node without a worktree.

## Row markers

Each worktree node's row shows its branch (`detached @ <base>` for a read-only one), how many commits it is ahead of its base (↑), how many files are uncommitted, a "changes" marker once it is done or exited with work not yet in its base, and "merged" after tiller merged it. The daemon recomputes this when the node's turn ends, about 15 seconds after it edits a file or runs a command (later edits push that back), when it exits, before a merge or close, and on start. `list_nodes` and `tl list` show the same counts on each worktree node's line (`⎇ branch from base ↑ahead ↓behind dirty merged`); the CLI's `/api/list_nodes` data carries them in each node's `worktree` field. `tl diff <id> [--stat]`, the MCP `diff` tool and the app's Diff tab show what the node changed since it branched, committed or not.

## Merging

The Merge button on the row or the exited card, `tl merge <id> [--close]` and the MCP `merge` tool bring a node's branch into its base. An agent may merge only its descendants, and the human approves each merge unless `approvals.merge` is true.

Tiller never merges into a protected branch: those named in `worktrees.protected` (default `main` and `master`) and the remote's default branch (`origin/HEAD`, when it is set). Such a merge is refused with nothing changed, and the error says to spawn workers with a base branch and open a pull request from it. The orchestrator prompt asks for one base branch per task, named after the repo's own branch convention, and for the orchestrator to hand that branch to the human to push. Setting `worktrees.protected` to `[]` turns protection off entirely, origin's default branch included, so merges go straight into `main` and a worker spawned from `main` keeps it as its base.

A merge is also refused, with nothing changed, while the node is working, when its worktree has uncommitted files, when the base branch is checked out somewhere with uncommitted changes, when the branch conflicts with the base, or when there is nothing to merge. The conflict check uses `git merge-tree`, which names the conflicting paths without touching any file; the MCP tool then replies `{ok: false, conflicts: [paths]}`, and the orchestrator prompt tells the orchestrator to send the worker a rebase instruction rather than resolve it. For the merge and squash styles the result is written with `git commit-tree`, which is passed `-S` when the repo's effective git config sets `commit.gpgsign` (commit-tree ignores that setting on its own); if signing fails, for example because the key or agent is unavailable, the merge is refused with git's error and the base is not moved. Then the base's checkout, if it has one, is fast-forwarded to the new commit, and a base checked out nowhere has its ref moved atomically.

`worktrees.mergeStyle` picks the style: `merge` (the default) always makes a merge commit, `squash` makes one commit on the base, and `ff-only` only fast-forwards and is refused once the base has moved on. You can also merge with git yourself; tiller notices the branch is merged.

## Close and kill

Closing a worktree node removes the worktree and deletes the branch, but only when the tree is clean, the branch is merged and no other live node works in it; otherwise the close is refused, with the counts, and nothing is closed. Two options decide instead: `tl kill <id> --keep-branch` (or `worktree: "keep"` on the MCP `close` tool) commits any changes as a WIP commit, removes the directory and keeps the branch, and `--discard` (`worktree: "discard"`) deletes both, unmerged work included; an agent's discard always needs the human's approval, whatever `approvals.close` says. `tl prune` keeps worktree nodes with unmerged work and lists them.

## tl worktrees

`tl worktrees [--cwd P]` lists node worktrees, orphans (worktrees left without a node, for example by a crash) and kept branches. `tl worktrees clean` removes the orphans and kept branches that are clean and merged; `--force` removes them all and prints the commits and files that went. On start the daemon removes orphans that hold no work and reports the rest.

## Setup and teardown

`worktrees.setup` commands run one by one with `sh -c` in a new worktree, after the include copy and before Claude starts, for example `{"worktrees": {"setup": ["npm ci"]}}`. Their environment has `TL_NODE_ID`, `TL_WORKTREE`, `TL_REPO`, `TL_BASE` and the daemon's login PATH. The node shows "setting up worktree: <command>" meanwhile. Output goes to `~/.tiller/nodes/<id>/setup.log`, and each command has 10 minutes. If one fails, the node is left exited and errored with the log's path in its activity; restarting it runs the setup again and then starts the agent with its original prompt. `worktrees.teardown` commands run the same way, best effort, before tiller removes any worktree. Neither runs unless Claude already trusts the repo, in any configured Claude account, or `tl trust` approved it.

## Tools that glob the tree

The daemon hides `.claude/worktrees/` from `git status` through `.git/info/exclude`, which ripgrep also honours, but test runners, linters and other tools that walk the directory tree do not, and they would find every worker's copy of the code. Exclude `**/.claude/worktrees/**` in them; this repo does so in `vitest.config.ts`.
