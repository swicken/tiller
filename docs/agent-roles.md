# Agents: what they are told and how their work is checked

## The system prompt

Every agent node receives Tiller instructions through its harness (Claude appends them to its own system prompt), so coordination is restored on launch and resume. The preamble, generated by `systemPrompt` in `src/daemon/launch.ts`, gives the node its id, title and parent, explains the message envelope (see [messaging.md](messaging.md)), forbids changing infrastructure or anything outside the machine (deploys, pushes, cloud or cluster mutations, publishing, sending data to external services) without the human's explicit permission, telling the node to ask its parent, or the human if it has none, tells a node with a parent to finish with `report_outcome`, and adds a paragraph about the session directory and, for a worktree node, about its worktree. The role section follows it under a `# Role` heading.

## Role prompts and overrides

A node's role is `orchestrator`, `worker` or `none`. By default a root node is an orchestrator and a node with a parent is a worker; `--role` on `tl new` and `tl spawn`, or `role` on the MCP `spawn` tool, sets it explicitly, and `none` leaves the role section out.

The role text is the built-in default (`DEFAULT_PROMPTS` in `src/daemon/launch.ts`) unless an override file exists. A file at `<repo>/.tiller/orchestrator.md` or `worker.md` wins for nodes whose directory is that repo; otherwise `~/.tiller/prompts/orchestrator.md` or `worker.md` applies to every repo. The files are read at each launch or resume, so an edit applies to the next node you start. `tl prompts` prints the files in effect for the current directory, or `built-in` where there is none.

The built-in orchestrator prompt tells the orchestrator to coordinate rather than do the work: split a task into independent streams, spawn one worker per stream with a self-contained brief, wait without polling, read each worker's outcome, have non-trivial changes reviewed by a node with the restricted `reviewer` preset on Claude or Pi, or the portable `reviewer` profile on Codex (at most two rounds before asking the human), check the diff, merge, and close finished workers. The built-in worker prompt tells the worker to do exactly its brief and to ask its parent, not the human, when the brief is unclear.

## Model, effort and permission mode

Model and effort resolve independently: explicit spawn argument, preset, selected harness/profile config, then legacy `roles` config for Claude only (`none` counts as worker). No built-in model or effort is forced. See [configuration](config.md) for the exact per-field project/home precedence and opt-in Codex example. Resolved selections persist across resume, restart and follow-up.

A Claude spawn without a permission mode inherits its same-harness parent's mode, except that `bypassPermissions` is never inherited, and only the human may spawn a node with `bypassPermissions`. Other harnesses retain their own permission policy.

## Task profiles

Task profiles select behavior independently of coordination roles. Select one with `--profile` on `tl new` / `tl spawn`, `profile` on MCP/WebSocket spawn, or the UI's Task profile chooser. Without an explicit or preset profile, the effective coordination role selects the default: `orchestrator` maps to `orchestrator`, while `worker` and `none` map to `implementation`. Ordinary roots therefore default to `orchestrator`, children to `implementation`. The UI follows role changes until you choose a profile explicitly. The five profiles are:

| Profile | Guidance |
|---|---|
| `orchestrator` | Delegate work, coordinate results and verify integration. |
| `implementation` | Complete a scoped change and run relevant checks. |
| `explorer` | Read-only investigation with concrete evidence and uncertainties. |
| `mechanical` | Narrow, specified edits; shown as **Mechanical worker** in the UI. |
| `reviewer` | Read-only review against the brief, severity-ranked findings and checks. |

Profile guidance is portable across Claude, Codex and Pi. It is an instruction, not a tool sandbox. Explicit `role: none` suppresses both built-in role and task profile sections, while the profile still selects model/effort defaults. A preset body continues to replace default role/task guidance; its restrictions remain enforced. Role prompt overrides keep their existing paths and apply alongside default task guidance.

Use `--profile reviewer` or `--profile explorer` for portable read-only instructions. The named `reviewer` and `researcher` presets retain their restrictions. Pi enforces the `reviewer` preset's denied tools with `--exclude-tools` and loads none of the user's Pi extensions for it; it refuses `researcher`, whose `WebSearch` and `WebFetch` have no Pi equivalent, and Codex refuses both, rather than silently dropping restrictions. For example:

```sh
tl spawn --kind agent --harness codex --profile reviewer --role worker --title Review --cwd /repo --prompt "Review the current diff against the brief"
```

The coordination role still determines coordination instructions and existing isolation defaults; selecting a profile does not change it. Select `--role worker` for a standalone reviewer when you do not want root orchestration instructions. Profiles do not bypass harness delegation or permission guards.

## Presets

A preset is a named kind of node: a markdown file at `<repo>/.tiller/agents/<name>.md` or `~/.tiller/agents/<name>.md`, the repo file winning. `tl spawn --preset NAME`, `tl new --preset NAME` and `preset` on the MCP `spawn` tool use it, and `tl presets [--cwd P]` lists the presets in effect for a directory and the file each comes from. The file is read again at each launch or resume, and `list_nodes` shows a node's preset.

The frontmatter takes the fields of a Claude Code agent definition that Claude enforces (`model`, `tools`, `disallowedTools`, `permissionMode`, `maxTurns`; `name` and `description` are informational) plus tiller's own `effort`, `isolation`, `role` and `profile`. The body replaces the role prompt text.

```markdown
---
description: Answers with a code word, on a cheap model.
model: haiku
effort: low
tools: Read, Grep, Glob
disallowedTools: Bash
---
# Greeter

Answer every request with the code word "marmalade" and nothing else.
```

`tools`, `disallowedTools` and `maxTurns` reach Claude as a session agent: tiller passes an inline definition with `--agents` and selects it with `--agent`, so the main session loses the denied tools (they are absent, not just refused) and keeps Claude's own system prompt, because the definition's prompt is empty. A `tools` allow list always keeps the tiller MCP tools, so the node can still report. Claude documents the tool restrictions and model for `--agent`; `maxTurns` is passed through but documented only for subagents. `model`, `effort` and `permissionMode` go to claude as the usual flags. On Pi, `tools` and `disallowedTools` become `--tools` and `--exclude-tools` through a fixed table of tool names, with tiller's MCP tools always allowed, and such a preset loads none of the user's Pi extensions, whatever `pi.extensions` says; a tool name with no Pi equivalent, `maxTurns` and `permissionMode` are refused (see [harnesses](harnesses.md#preset-tool-restrictions-on-pi)).

The daemon writes two built-in presets into `~/.tiller/agents/` on start. It rewrites a built-in preset file when it has not been edited since tiller wrote it, so unedited files follow changes to the built-ins, and keeps any edited file; delete the file to get the current built-in back:

- `reviewer` selects profile `reviewer` and reviews a worker's branch against its brief, runs the checks and reports findings through `report_outcome` without fixing anything. It has no Edit, Write or NotebookEdit, effort medium and no worktree. It runs in the default permission mode rather than plan mode, because plan mode makes Claude ask the human before every tiller tool call, `report_outcome` included; without Edit and Write, default mode still asks before any shell command that would change files, unless your own Claude settings allow it.
- `researcher` selects profile `explorer` and answers a question from code and the web. It has only Read, Grep, Glob, WebSearch and WebFetch, so no shell.

## Spawn limits

An agent's spawn is refused when the new node would sit more than `limits.maxDepth` levels below its root, when its parent already has `limits.maxChildren` live children, or when `daemon.maxLiveNodes` nodes are live. The error names the limit and tells the agent to reuse an idle worker or close finished ones. The human's spawns are exempt.

## report_outcome

A worker ends its task by calling `report_outcome` with `succeeded` or `failed`, an optional `note`, and the structured fields `summary` (what it did), `changedFiles` (paths), `verified` (what it ran to check the work, and the result) and `openQuestions` (what is left for the parent to decide). The parent reads these from `list_nodes` instead of reading the transcript; the app shows them in the last-message panel and on the exited card. The daemon tells the parent of every recorded outcome (see [messaging.md](messaging.md)).

## The completion gate

The `gate` config key makes a `succeeded` report wait for a check, for example `{"gate": {"command": "npm test"}}`. The daemon runs the command with `sh -c` in the worker's directory, with the daemon's login PATH and `TL_NODE_ID` in the environment (plus the worktree variables of [worktrees.md](worktrees.md) for a worktree node), and appends its output to `~/.tiller/nodes/<id>/gate.log`; the node shows "gate: <command>" meanwhile and its row carries a gate marker. The gate runs only when Claude already trusts the directory. A worktree node reads the key from the main checkout's project file.

If the command passes, the outcome is recorded with `gate: "passed"`. If it fails, nothing is recorded and the worker is told, with the last 60 lines of output, to fix the problem and report again. The reply to `report_outcome` carries the result when the gate finishes within 30 seconds; otherwise the reply says the gate is pending and a failure arrives later as a message. Any report made while the gate is still running is refused. After `gate.retries` further failures the outcome is recorded as failed with `gate: "failed"`. Each run is stopped after `gate.timeoutMinutes`. `tl gate [--cwd P]` runs the configured command once in a directory and prints the result, so you can try it.

This repository's `.tiller/config.json` configures the automatic gate to run `npm run typecheck` (root and Pi adapter) and the UI typecheck. It does not select or run focused tests. Implementation workers must run relevant focused tests for their changes and report the commands and results. Reviewers run targeted checks as needed; read-only analyses do not need broad testing.

The orchestrator must run the full Vitest suite (`npm test`) once on the final integrated tree before publication. These focused and integration checks are manual responsibilities in addition to the automatic gate. CI remains authoritative for types, the full Vitest suite, release helpers, the production UI build and native Rust checks; see [AGENTS.md](../AGENTS.md) and [the CI workflow](../.github/workflows/ci.yml).
